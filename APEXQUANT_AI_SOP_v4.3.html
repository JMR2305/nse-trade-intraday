1. Executive Summary

1.1 What is ApexQuant AI?

ApexQuant AI is a paper-only NSE trading research platform built on a multi-agent AI architecture. Its core purpose is to:

  • Scan NIFTY 50 (51 symbols after TATAMOTORS demerger) every 5 minutes during market hours
  • Run each symbol through a multi-layer AI pipeline: data quality → signal → strategy → risk → decision → execution
  • Generate BUY / WATCH / IGNORE recommendations with confidence scores, opportunity scores, and position-sizing guidance
  • Execute paper (simulated) trades when all gates pass, building a tracked portfolio
  • Learn from the outcomes of those paper trades to improve future decisions

No live orders have ever been placed, and no Zerodha broker APIs are called for order submission. Live execution is structurally disabled.

3. Full Pipeline Flow

3.1 Main Scan and Execution Pipeline


START SCAN TICK (every 5 minutes, 09:15–15:30 IST)
│
├── [STEP 1] Scan Lock Acquired (DB-durable, prevents concurrent scans)
│
├── [STEP 2] Data Fetch: LiveDataProvider.fetch_batch(universe)
│   │   Provider: Yahoo Finance (yfinance) — the ONLY OHLCV source
│   │   Interval: 1d (daily bars), Period: 6mo
│   │   Kite: NOT involved in this step.
│   └── Output: {symbol: SymbolFetchResult} — OHLCV + age_days + quality per symbol
│
├── [STEP 3] For each of 51 symbols: _scan_one()
│   │   [SIGNAL] Compute indicators: RSI, MACD, Bollinger, ADX, OBV
│   │   [DATA QUALITY GATE] _apply_quality_gate()
│   │   [R:R GATE] rr_ratio < 1.5 → downgrade to WATCH
│   │   [MARKET CONTEXT] Apply regime modifier
│   │   [OPPORTUNITY SCORE] trade_quality×0.40 + confidence×0.30 + rr×0.20 + market×0.10
│   │   [STRATEGY] Select MOMENTUM / BREAKOUT / MEAN_REVERSION
│   └── Output: Phase7Recommendation per symbol (entry_price = yfinance daily close)
│
├── [STEP 3B] Kite LTP Overlay Loop (when KITE_LTP_OVERLAY_ENABLED=true)
│   │   kite_ltp_overlay.fetch_ltp_overlay(all_symbols) — ONE bulk Kite call
│   │   For each rec: apply_overlay_to_rec(rec, overlay)
│   │   Option A invariants:
│   │     indicator_source    = "yfinance_daily_bars"  ← NEVER changes
│   │     ohlcv_source        = "yfinance_daily_bars"  ← NEVER changes
│   │     current_price_source becomes "kite_live_ltp" when LTP available
│   │     execution_price_source becomes "kite_live_ltp" when LTP available
│   └── Graceful fallback to yfinance close if Kite session unavailable
│
├── [STEP 4] Snapshot saved to DB (canonical scan_id)
│
├── [STEP 5] For each BUY signal: phase20_executor.execute_buy()
│   │   [PRECHECK] capital_available, exposure_cap, circuit_breaker
│   │   [RISK] rv_result from risk_agent
│   │   [EXECUTION] create trade row in phase20_paper_trades
│   │   [FILL PRICE] Kite LTP if available, else yfinance daily close
│   │   [TRADE ID] P20-{uuid} — always P20- prefix
│   │   [PIPELINE EVENTS] ORDER_SUBMITTED → ORDER_EXECUTED (P20- trade_id)
│   │   ← Guardrail: non-P20- trade_ids in LIVE mode are rejected at emit layer
│   └── Output: P20- trade in phase20_paper_trades
│
└── [STEP 6] Exit management: phase20_exits.manage_open_positions()
    │   [LTP FETCH] Kite LTP for exit quote when flag=true + session verified
    │   [EXIT RULES] 8 rules evaluated against live or daily-close price
    │   [REALIZED PNL] recorded only when quote_reliable=True
    └── EXIT_PENDING → CLOSED with realized_pnl when Kite LTP available

11. Detailed Case Studies

11.1 DRREDDY — Repeated BUY Rejected (RESOLVED)

On every market day since Aug 8, DRREDDY generated BUY signals that passed all gates except the 20% position-size cap. Root cause: 8 shares × ~₹1,350 = ₹10,800 = 21.6% > 20.0% cap. Resolution: ✅ FIXED in Bug Audit Task 1. cap_qty=7 (7 × ₹1,350 = 18.9%) → proceeds to execute_buy().

11.2 Aug 11 Phantom Executions (CONFIRMED + GUARDRAIL ACTIVE) [UPDATED v4.3]

Verdict: CONFIRMED PHANTOM. DB-confirmed: 63 ORDER_EXECUTED events in pipeline_events, 0 rows in phase20_paper_trades. Trade IDs use BTT- prefix (external backtest_portfolio / replay process — not canonical executor). Scan-loop ran 88 times, up to 5/minute; same signal fired repeatedly.

v4.3 prevention (three independent layers):

  1. Emit layer: pipeline_events._emit_unsafe() blocks ORDER_* events with non-P20- trade_ids in LIVE mode. Any future BTT- ORDER_EXECUTED never reaches the DB. Warning is logged.
  2. SQL layer: buy_audit.py DB query adds AND (payload->>'trade_id' IS NULL OR payload->>'trade_id' LIKE 'P20-%') — filtering any historical non-canonical rows that already exist in the table.
  3. Application layer: validation_engines.py, phase26_consistency.py, phase26_live_monitor.py all apply _is_canonical_order_event() / P20- prefix check before counting executions.
Test proof: test_aug11_phantoms_not_counted_by_is_canonical — 63 BTT- events + 1 P20- event → only 1 counted. All 18 tests pass at 0.67s.

27. BTT/Replay Event Namespace — Guardrail Implementation [NEW v4.3]

27.1 Problem Background

On 2026-08-11, the scan-loop runaway produced 88 scans and the backtest_portfolio.py replay process emitted 63 ORDER_EXECUTED events to the pipeline_events table with BTT- prefixed trade_ids. These events produced 0 rows in phase20_paper_trades (the canonical ledger) because the replay engine writes to backtest_trades — a separate table. However, any dashboard or validation code counting ORDER_EXECUTED events from pipeline_events without a trade_id prefix filter would miscount these as 63 real paper executions.

27.2 Root Cause

backtest_portfolio.py line 984 generates BTT-{uuid[:10]} trade IDs as a fallback. The replay run wrote these to pipeline_events (LIVE mode, because mode defaults were not overridden) using the same ORDER_EXECUTED event type as the canonical phase20 executor. No consumer distinguished canonical P20- events from BTT- replay events.

27.3 Fix — Three Independent Layers

Layer 1: Emit-Level Guardrail (pipeline_events.py)


# _CANONICAL_ORDER_TYPES = frozenset({
#   "ORDER_SUBMITTED", "ORDER_EXECUTED", "ORDER_REJECTED", "ORDER_CANCELLED"
# })

def _emit_unsafe(event_type, stage, *, scan_id, symbol, payload, mode, run_id, ts=None):
    # Guardrail: ORDER_* in LIVE mode must carry a P20- trade_id.
    if event_type in _CANONICAL_ORDER_TYPES and mode == "LIVE":
        _tid = str((payload or {}).get("trade_id") or "")
        if _tid and not _tid.startswith("P20-"):
            logger.warning(
                "pipeline_events: BLOCKED non-canonical %s (trade_id=%s) — "
                "only P20-... IDs may use ORDER_* event types in LIVE mode. "
                "Call emit_replay() for backtest/replay events.",
                event_type, _tid,
            )
            return  # ← discarded, never reaches DB
    ...

Behaviour:

  • BTT- ORDER_EXECUTED in LIVE mode → blocked + WARNING logged
  • P20- ORDER_EXECUTED in LIVE mode → passes through (canonical)
  • BTT- ORDER_EXECUTED in BACKTEST mode (via emit_replay()) → allowed
  • Events with no trade_id → allowed (backward compatible)

Layer 2: New emit_replay() Helper


def emit_replay(event_type, stage, *, scan_id=None, symbol=None,
                payload=None, run_id=None, ts=None) -> None:
    """Emit a BACKTEST-mode event — never in LIVE pipeline_events stream."""
    p = dict(payload or {})
    p["source"] = "replay"
    p["canonical_trade"] = False
    emit(event_type, stage, ..., mode="BACKTEST", ...)

New event types for backtest use:

  • REPLAY_ORDER_SUBMITTED — use instead of ORDER_SUBMITTED for replay fills
  • REPLAY_EXECUTION_COMPLETED — use instead of ORDER_EXECUTED
  • REPLAY_ORDER_REJECTED — use instead of ORDER_REJECTED
