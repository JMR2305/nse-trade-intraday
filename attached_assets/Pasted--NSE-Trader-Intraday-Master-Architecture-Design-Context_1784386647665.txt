# NSE Trader Intraday - Master Architecture Design

## Context

This project is a separate Intraday Trading platform created from the existing Swing Trading platform.

The Swing project must remain completely untouched.

A project strategy and phased architecture plan has already been approved. We will now begin with architecture documentation and Phase 0 planning only.

## 4. Mid-Session Recovery Architecture

Design recovery behavior for a crash or deployment restart during market hours.

The system must restore:

- Current intraday session
- Open paper positions
- Pending orders
- Stops and targets
- Entry-time features
- Maximum holding timers
- Square-off timers
- Latest completed bars
- Market-data subscription state
- Risk usage
- Session realized and unrealized P&L

Define the restart flow:

Process starts
→ Load current session
→ Restore internal state
→ Reconnect market data
→ Reconcile positions and orders
→ Restore monitoring
→ Resume or enter safe mode

PostgreSQL must be the recovery source of truth.

## 5. Continuous Trade Monitoring

Design a first-class Position Monitoring Service.

Every open position must be checked for:

### Tick-level checks
- Stop-loss
- Profit targets
- Abnormal spread
- Tradability and liquidity
- NSE upper/lower circuit conditions

### Completed-bar checks
- Maximum holding time
- Strategy thesis invalidation
- VWAP failure
- ORB failure
- Momentum deterioration
- Market-regime deterioration
- Time-of-day exit rules

### Portfolio checks
- Daily loss cap
- Maximum open positions
- Sector exposure
- Correlation exposure
- Total capital at risk
- Mandatory square-off boundary

The position-monitoring service must be independent from the strategy that created the entry.

------------------------------------------------------------

## 6. Independent Watchdog

Design a watchdog that is independent of trading strategy logic.

It must monitor:

- Trading-engine heartbeat
- Market-data service heartbeat
- WebSocket state
- Last tick age per active symbol
- Last completed-bar age
- FastAPI liveness
- Node API liveness
- PostgreSQL health
- Memory and resource usage
- Position and order reconciliation
- Square-off completion
- Watchdog's own health

Define heartbeat frequency, stale thresholds and escalation behavior.

------------------------------------------------------------

## 7. Kill-Switch Policy

Design three separate controls:

### Pause New Entries
Blocks all new entries while existing trades continue to be monitored.

### Cancel Pending Orders
Cancels all unfilled entry orders without disabling protection for open positions.

### Flatten All
Cancels pending entries and closes every open position using the emergency execution policy.

Define:

- Automatic triggers
- Manual authority
- Authentication
- Confirmation behavior
- Idempotency
- Audit trail
- Whether each action can be reversed
- Dashboard presentation

------------------------------------------------------------

## 8. Square-Off Escalation

Design mandatory session square-off behavior:

1. 15:15:00 IST
   Attempt exit using the configured executable limit price.

2. 15:15:30 IST
   Cancel unfilled orders and resubmit according to the emergency market-order policy.

3. 15:16:00 IST
   Retry and trigger a Critical alert.

4. 15:20:00 IST
   If any position remains open, create an Incident and disable all new trading until resolved.

Account for:

- Exchange outage
- Broker outage
- Stock price bands
- No liquidity
- Rejected orders
- Partial fills
- Network failure
- Process restart

## 10. Feature and Strategy Architecture

Version 1 should use a transparent heuristic market-regime tagger rather than a learned classifier.

Initial features should include:

- Session-reset VWAP
- VWAP standard-deviation bands
- Relative volume by time slot
- Opening range
- Gap percentage and gap type
- Time-of-day encoding
- ATR and volatility percentile
- ADX and directional movement
- Bid-ask spread
- Liquidity
- NIFTY trend and volatility
- Sector-relative strength

Initial research strategies:

- Opening Range Breakout
- Momentum Burst
- Trend Pullback
- VWAP Reversion
- Gap-and-Go
- Gap-Fill

Define a common strategy interface.

## 11. Expected Value and Probability Definition

For version 1 define:

Loss Probability = 1 - Win Probability

unless a separately validated multi-outcome model is introduced.

Use expected net value as the main ranking measure:

Expected Value =
(Calibrated Win Probability × Expected Reward)
-
(Loss Probability × Expected Loss)
-
Brokerage
-
Taxes and exchange charges
-
Spread
-
Slippage
-
Any supported event-risk penalty

Do not include an event-risk penalty unless a real event-data source exists.

------------------------------------------------------------

## 12. Calibration Separation

Define strict separation between:

- Swing calibration model
- Intraday calibration model

Requirements:

- Separate model artifacts
- Separate versioning
- Separate training queries
- product_type required at database level
- No fallback to the swing calibration model
- Uncalibrated output clearly labelled during cold start
- Every prediction records model version
- Retraining controlled by governance and drift checks

Also design a single Confidence Aggregator so multiple modules do not independently modify confidence.

## 14. Latency Budgets

Use these initial engineering targets:

- Tick received to market-state update: under 250 ms
- Completed bar to feature update: under 500 ms
- Feature update to signal and risk decision: under 750 ms
- Approved decision to paper-order submission: under 500 ms
- Total completed-bar to paper-order submission: under 2 seconds

Define how each stage will be measured and logged.

------------------------------------------------------------

## 15. Alert and Incident Levels

Define:

### Informational
Normal session, entry and exit events.

### Warning
Single reconnect, elevated spread or approaching data-staleness threshold.

### Critical
Heartbeat loss, position mismatch, risk breach or square-off retry.

### Incident
Position still open after 15:20, repeated reconciliation failure or watchdog failure.

Critical and Incident conditions must trigger automatic mitigation where possible, not only notifications.
