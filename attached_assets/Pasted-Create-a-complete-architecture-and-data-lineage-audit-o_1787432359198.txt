Create a complete architecture and data-lineage audit of the entire NSE-Trade-Intraday application.

PURPOSE

We want a visual and technical map of the complete project showing:

- every frontend page
- every visible field, metric, card, table, chart, button and status
- where each displayed value comes from
- which API endpoint supplies it
- which backend service calculates it
- which repository/database table stores it
- which external system supplies the raw data
- how pages and backend modules connect to one another
- the full end-to-end flow of the application

This will become the master “vision map” of the Intraday project.

DO NOT modify production code.

PHASE 1 — PAGE INVENTORY

Identify every currently reachable frontend page for:

- web
- mobile
- admin/internal pages
- replay/research pages
- pre-open pages
- portfolio/risk pages
- execution/order pages
- health/system pages
- settings/configuration pages

For every page report:

- route
- component file
- page title
- purpose
- navigation entry
- API hooks used
- refresh/poll interval
- whether data is live, cached, historical, demo, seeded or calculated

PHASE 2 — FIELD-LEVEL DATA LINEAGE

For every visible field on every page, create a row containing:

1. Page
2. UI section/card/table
3. Displayed field
4. Frontend component
5. Frontend variable/property
6. Hook/query/function
7. API endpoint
8. HTTP method
9. Backend route handler
10. Service/business-logic function
11. Formula/calculation
12. Repository/data-access function
13. Database table/column
14. External data source
15. Refresh frequency
16. Persistence type
17. Live vs seeded/demo
18. Fallback behavior
19. Error behavior
20. Notes/risks

PHASE 3 — API INVENTORY

Create a complete API map:

- endpoint
- method
- route file
- caller/page
- service
- input parameters
- output schema
- database dependencies
- Zerodha dependencies
- cache dependencies
- scheduler dependencies
- paper-trading dependencies
- whether endpoint modifies state

PHASE 4 — DATABASE MAP

Inventory all active tables/models.

For each:

- table/model name
- purpose
- writer
- reader
- related pages
- primary keys
- important fields
- relationships
- retention behavior
- whether live, replay, audit, cache or configuration data

Map every external dependency:

- Zerodha Kite
- market-data providers
- email/notification systems
- GitHub if runtime-relevant
- database
- scheduler
- caches
- external AI/model providers if active

Show exactly where each external system enters the architecture.

Create Mermaid diagrams for:

For every important page create its own Mermaid diagram showing:

Page
→ component

PHASE 9 — DATA QUALITY AUDIT

Flag:

- seeded/demo values
- hardcoded values
- stale data
- duplicated calculations
- same metric calculated differently in different places
- API fields not consumed by UI
- UI fields with unclear backend source
- dead endpoints
- dead frontend hooks
- pages reading obsolete tables
- values that can become negative/impossible
- missing refresh
- missing error handling

Do not fix anything yet.

Create:

1. INTRADAY_MASTER_ARCHITECTURE.md
2. INTRADAY_PAGE_DATA_LINEAGE.csv

6. INTRADAY_DATA_QUALITY_AUDIT.md

The master architecture document must reference the detailed files.

- audit date
- total pages
- total API endpoints
- total DB tables/models
- total frontend fields traced
