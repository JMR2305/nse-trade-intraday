# RC-10D — BROKER LAYER IMPLEMENTATION PROMPT

## Objective

Implement RC-10D: Broker Integration Layer for the NSE Intraday Trading Platform.

This phase must connect the existing trading platform to Zerodha Kite while preserving all frozen architecture and safety controls.

DO NOT implement RC-10C Portfolio Management in this batch.

DO NOT rewrite RC-7 Execution Engine.

The Broker Layer must operate underneath RC-7 and must never allow broker APIs to bypass:

- RC-8 Risk Engine
- RC-7 Execution Engine
- Existing kill switch
- Existing idempotency controls
- Existing execution state machine
- Existing audit and recovery mechanisms

The required production flow is:

Strategy
→ SignalRouter
→ RC-8 Risk Engine
→ RC-7 Execution Engine
→ RC-10D Broker Abstraction
→ Zerodha Kite API

Broker updates must flow back through:

Zerodha WebSocket / REST
→ RC-10D Broker Layer
→ RC-7 Order State and Recovery
→ Persistence and Audit Logs

RC-10B AI Forecast remains advisory-only and must not be modified except for essential compatibility fixes.

------------------------------------------------------------
7. IDEMPOTENT ORDER SUBMISSION
------------------------------------------------------------

Order placement must be idempotent.

Before broker submission:

- require an internal execution order ID
- create a deterministic idempotency key
- persist the pending submission
- check whether the same internal order was already submitted
- prevent accidental duplicate orders after timeout or restart

If the broker response is uncertain:

- do not immediately resubmit
- reconcile using order book, tag, exchange order ID, timestamp, symbol, quantity, price, and side
- classify the result as confirmed, rejected, unresolved, or duplicate

Never assume a timeout means the broker did not receive the order.

14. RETRY POLICY
------------------------------------------------------------

Implement bounded retries only for retry-safe operations.

Safe candidates may include:

- GET requests
- session validation
- funds and margin retrieval
- order-book retrieval
- reconciliation queries

Order placement must not be blindly retried.

For uncertain order placement:

- enter reconciliation flow
- search broker state
- determine whether the order exists
- only resubmit when conclusively safe

Use:

- exponential backoff
- jitter
- retry classification
- maximum attempts
- structured logging

16. PAPER TRADING MODE
------------------------------------------------------------

Paper trading must remain the default mode.

In paper mode:

- do not send live orders to Zerodha
- allow authentication, market reads, instruments, margins, positions, and account information where appropriate
- simulate order submission through the existing paper execution path
- clearly label every response as paper or live
- prevent accidental mode mixing

Live order submission must require all of the following:

- explicit configuration
- valid authenticated session
- application-level live-trading enablement
- RC-8 approval
- RC-7 approved command
- kill switch not active
- trading session valid
- broker health acceptable

No single boolean should be sufficient to enable live trading accidentally.
